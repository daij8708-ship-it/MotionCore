# 基于 Qt/C++ 与 STM32 的工业运动控制及实时监测系统

[![构建与测试](https://github.com/daij8708-ship-it/MotionCore/actions/workflows/ci.yml/badge.svg)](https://github.com/daij8708-ship-it/MotionCore/actions/workflows/ci.yml)

一套**结构分层、协议可靠、可测试、可扩展**的运动控制与上位机监控系统：Qt6 上位机 +
零 Qt 依赖的协议与算法核心库 + 进程内虚拟设备，三者构成一条"连接 → 握手 → 下发命令 →
遥测入库 → 曲线呈现 → 链路故障与恢复"的完整闭环。

## 已实现的功能

**协议与算法核心库**（`common/`，零 Qt 依赖）：二进制帧协议 v3（CRC-16/CCITT-FALSE 校验、流式
拆包、坏帧分类计数）；载荷编解码（结构合法性与语义合法性两级校验，浮点按 IEEE-754 小端位模式）；
应答跟踪与超时处置（重传 / 故障 / 丢弃三类归宿，**运动指令永不自动重传**）；有界环形缓冲；
设备侧序列号去重与重放应答；心跳调度、RTT 采样与链路失效判定，超时窗口按实测 RTT 自适应。
另有**工艺配方模型与校验**、**任务/程序调度引擎**（一步在途、"不确定就停"）、**报警分级与代码表**、
**软件联锁规则表**、**操作员权限与操作审计**、**回零流程与软限位**，以及**多轴同步移动的规划**
（速度缩放式：按最长行程定公共时长，其余轴按比例慢下来 —— 于是同时出发即同时到达）与
**运行日志**（分级过滤 + 有界环形 + 按大小滚动）的核心语义。
协议全文见 `docs/PROTOCOL.md`。

**设备侧**：8 状态 × 12 事件状态机（命令门禁逐格定义，故障锁存**只能由人工确认清除**）
+ 通信丢失保护（链路静默超窗即撤销目标、限幅停车并进入故障）；进程内虚拟设备模拟器，
与上位机链接**同一份**协议实现；另有可执行程序 `tools/mc_sim` —— 它让**真上位机**在没有
STM32 的情况下，通过一条**真串口或伪终端**与协议等价的对端通信（同一套帧格式、同一个状态机、
同一个运动模型）。运动模型含机械惯性、编码器量化与"在固定窗口上差分量化位置"的速度估计、
带抗积分饱和的 PI(D) 闭环；设备侧还实现**回零**（把到位处定义成零点，并用一帧持续上报的状态位
如实回答"这一轮成没成"）与**软限位执法**（越限即撤输出并进故障）。

**固件支线**（`firmware/`，STM32F103C8T6）：与上位机共用同一张状态机与协议常量的最小固件 ——
同一套帧格式、CRC、命令、去重、遥测与故障处理；USART1 中断收 + 环形缓冲、SysTick 1 ms 时基、
TIM3 10 kHz PWM、TIM4 四倍频编码器输入（PB6/PB7）、TB6612 双方向输出（AIN1=PA7、AIN2=PB0）。
宿主端用 `common/` 的编解码器做独立参照，**20 条测试**含一条**真 PTY 端到端**
（`mc_fw_sim` 用与 STM32 完全相同的固件核心扮演设备，真上位机可以先连它）。
交叉编译产物为 `mc_fw_stm32f103.elf`（text 8623 B / bss 272 B）。已在 Blue Pill + TB6612FNG +
N20 编码器电机上完成烧录（OpenOCD Verify OK）、真串口会话、开环驱动与编码器速度闭环
（目标 200 deg/s，实测 202 deg/s）；位置环、真机回零/软限位与拔线保护**尚未验证**。
详见 `firmware/README.md`。

**上位机**（`host/`，Qt6，五层单向依赖核心库）：设备总览页（会话状态、握手轮次、链路 RTT 与
心跳统计、遥测计数、最近报警）；运动控制页（模式、使能与启动、目标值、PID 参数、手动停止、
**回零与回零进度**，每条命令在记录表里留下带归宿的结果）；数据曲线页（速度 / 位置 / 目标三条曲线，
min/max 分桶抽稀 + 定频刷新，各用独立纵轴）；PID 参数页（整定的唯一写入口，按 seq 与应答配对，
**软限位下发与参数回读**）；故障报警页（当前故障与锁存状态、"确认清除"、报警记录）；
历史数据页（SQLite 落库的会话 / 样本 / 事件 / 命令查询与 CSV 导出）；系统设置页（数据源、
串口参数、**当前生效的操作员角色**）；通信调试页（只读计数 + 故障注入）；**工艺配方页**
（保存 / 下装 / 逐步核对回读）；**任务页**（编写程序、逐步执行到被确认的结局）；
**双轴协调页**（把两台独立驱动器当一个组来用：连两轴、预览公共时长与各轴速度、协调启动；
**任一轴故障即 STOP 全组**）；**运行日志页**（按级别过滤、查看日志文件与滚动情况）；
会话生命周期（自动握手、一轮失败退避重开、链路失效后自动重连）。

**验证手段**：**409 条自动化测试**（协议核心 286 + 上位机 101 + 无头自检 2 + 固件 20，
其中 31 条端到端 + 1 条固件 PTY 端到端）；
进程内回环链路与故障注入（断开上行 / 断开下行 / 丢字节 / 损坏 / 延迟）；六种链路条件下的
端到端演示程序（`tools/mc_loopback_demo`，无需 Qt 与硬件）；**伪终端（PTY）上的真 tty 验证**
（设备端与上位机串口路径各一套，不需要任何硬件与外接工具）；单线程负载实测工具
（`host/mc_host_bench`，可把设备产帧周期设成 1 ms 造 10 倍压力）。详见
`docs/TEST_REPORT.md` 与 `docs/PERF.md`。

## 构建与测试

> **本项目的构建与测试在 WSL `Ubuntu-22.04` 中进行。**
> Windows 主机侧没有 `cmake` / `g++` / `qmake`（已实测），无法直接构建。

### 前置依赖

```bash
sudo apt install cmake g++ libgtest-dev          # 协议核心库与它的测试只需要这些
sudo apt install qt6-base-dev libgl-dev          # 上位机（host/）另需 Qt6 与 OpenGL 头文件
sudo apt install fonts-noto-cjk                  # 界面是中文的，缺中文字体会显示成方框
```

`libmc_core` 与它的测试**不需要 Qt**，第一条命令即可完成全部构建与测试。

> **Qt6 口径更正（2026-10-16）**：本文件此前写着"Qt6 已装好并实测编过跑过" ——
> **那句话当时是错的**。当时只验证了 Qt **Core**（一个无头 console 小程序），
> 而 `Qt6Widgets` 因为缺 `libgl-dev`（`/usr/include/GL/gl.h` 不存在 → `find_package(OpenGL)` 失败
> → `WrapOpenGL` 失败 → Widgets 连带失败）**压根配不上** —— 也就是说界面代码一行都没编译过。
> 装完 `libgl-dev` 之后才真正打通：`mc_host` 现在能编译、能在无头下渲染出图、能在 WSLg 下开窗。
> `fonts-noto-cjk` 同理是**"界面能不能读"的前置条件**而不是可选项：缺它时截图里中文全是方框（已实测）。

找不到 Qt6 时 `host/` 会**安静跳过**（打一条警告），协议核心库照样能构建与测试 —— ADR-001 不受影响。

### 构建与运行测试

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j"$(nproc)"
ctest --test-dir build --output-on-failure
```

`ctest` 会逐条列出每个 `TEST`（根工程 **389 条** = 协议核心 286 + 上位机 101 + 无头自检 2）。
固件支线是独立工程，**20 条**（帧/CRC 6 + 设备命令与安全 12 + 外部反馈 1 + 真 PTY 端到端 1）：

```bash
cmake -S firmware -B firmware/build -DCMAKE_BUILD_TYPE=Debug
cmake --build firmware/build -j"$(nproc)"
ctest --test-dir firmware/build --output-on-failure
```
直接运行测试二进制可看 gtest 自己的汇总：

```bash
./build/common/tests/mc_core_tests        # 协议核心（零 Qt）
./build/host/tests/mc_host_core_tests    # 上位机数据层与设备管理器（不需要图形平台）
./build/host/tests/mc_host_ui_tests      # 界面冒烟（自动用 offscreen 无头跑）
```

只想要协议核心（例如没装 Qt 的机器）：加 `-DMC_BUILD_HOST=OFF`。

### 把上位机跑起来（不需要任何硬件）

```bash
QT_QPA_PLATFORM=xcb ./build/host/mc_host     # WSLg 下开窗，窗口出现在 Windows 桌面上
```

> **为什么要显式写 `QT_QPA_PLATFORM=xcb`**：这台机器的 Qt 装了 8 个平台插件
> （`xcb / offscreen / minimal / vnc / linuxfb / eglfs / minimalegl / vkkhrdisplay`），
> **唯独没有 `wayland`**；而 WSLg 会同时给出 `WAYLAND_DISPLAY` 与 `DISPLAY`，
> 于是 Qt 先去试 Wayland、失败、再退回 xcb —— 能跑，但会多打一行
> `qt.qpa.plugin: Could not find the Qt platform plugin "wayland"`。
> 显式指定 `xcb` 就没这行噪声（实测：13 条判据全 ok，退出码 0）。
> 想用 Wayland 就另装 `qt6-wayland`，本项目不需要。

窗口里能做的：点「连接设备」→ 会话**自己**握手（总览页显示"就绪 / 共 1 轮"）→
运动控制页选模式 →「下发模式」→「使能并启动」→「下发目标」；
每一步都会在命令行表格里留下一条**带结果**的记录（已确认 / 被拒绝 + 原因 / 超时）。
「断开上行 / 断开下行 / 上行延迟」是**故障注入**按钮：点下去立刻能看到
会话作废 → 报警 → 自动重连（总览页的"最近报警"与"握手轮次"会跟着变）。

### 在没有硬件时扮演设备（`mc_sim`）

上位机需要一条**真串口**时，用 `mc_sim` 扮演设备对端。它跑的是与进程内模拟器**同一个**
`DeviceSimulator`，因此线上行为一致，差别只在于真的走了一条 tty：

```bash
./build/tools/mc_sim --pty                  # 开一对伪终端，打印从端路径
./build/tools/mc_sim --port /dev/ttyUSB0    # 在真串口上扮演设备
```

`--pty` 会打印一行 `/dev/pts/N`。把它填进上位机「系统设置」页的端口名、点「应用数据源」，
就能在界面上看到一条真正经过内核 tty 的会话（该页会显示当前生效的数据源与串口参数）。
其余选项：`--rate`（tick 频率）、`--kp/--ki/--kd`（设备侧整定初值，**默认全 0 是有含义的**：
速度环退化成纯前馈、位置环因为没有反馈增益不会动）、`--corrupt-every N`（上行每第 N 个字节
取反，造 CRC 错）、`--fault`（持续注入故障码）、`--ticks N`。

### 设备侧自检

```bash
./build/tools/mc_sim --self-test
```

`--self-test` 在伪终端上跑一段完整会话并逐条判 **51 项检查**：① 干净链路的握手 → 选环 → 使能 →
给目标 → 停车；② 上行损坏时 CRC 错必须被上位机拒掉、而链路整体仍然可用（好帧照常入库）；
③ 上位机"不说话了"时设备自己判通信丢失（**F7**）、锁存故障、并且只有显式确认之后才回 Ready；
④ **回零**（时限内走完并回到就绪、"本轮回零已建立零点"这一位进入时清零 / 完成才置位、
被打断的那一趟**状态上分不出来**但该位不会被读成"已建立"）与**软限位**
（下发落地、越限即撤输出进 OverLimit、关掉就一律不判）。
任何一条不满足就以非 0 退出，因此它和 `mc_host --selftest` 一样可以挂 CI（已进 `ctest`）。

> **边界（必须说清）**：伪终端是内核提供的**真 tty**，读写路径与真串口完全相同，
> 但它**不是电气层** —— 波特率、校验位在 PTY 上只是被记录、不起作用，所以
> "115200 能不能跑满 100 Hz 遥测"这类问题在这里**测不出来**。
> `--port` 走真串口的那条路，在开发环境里没有硬件可验，属**未验证代码**；`--pty` 与
> `--self-test` 是已验证的部分。

### 无头自检（带判据，可挂 CI）

```bash
QT_QPA_PLATFORM=offscreen ./build/host/mc_host --selftest=3
QT_QPA_PLATFORM=offscreen ./build/host/mc_host --selftest=5 --shot-prefix=/tmp/shot
```

`--selftest` 不是"演示一下"：它脚本化地跑一遍 连接 → 选模式 → 启动 → 下发目标 / PID，
打印实测摘要并逐条判 **13 条判据**，任何一条不满足就以非 0 退出。
加 `--shot-prefix` 会把各页各存一张 PNG（无头环境下要看界面长什么样就靠它）。

### 跑端到端演示

把上位机会话与虚拟设备用进程内回环连起来，打印六种链路条件下的实测摘要
（健康 / 上行损坏 / 下行全丢 / 低延迟 / 高延迟未开监控 / 高延迟已开监控）：

```bash
./build/tools/mc_loopback_demo
```

> 该程序里的**全部数据都是仿真**：没有 STM32、没有电机、没有真实串口。
> 它证明的是"协议在链路上真的按设计工作"，不是任何硬件指标。

> 场景 ⑤ 与 ⑥ 是**同一组链路条件**，唯一差别是有没有开链路监控：
> ⑤ 判 Fault 2（**误判** —— 应答其实在路上，只是比硬编码的 200 ms 窗口慢），
> ⑥ 判 Fault 0。这就是"按实测 RTT 配超时窗口"的价值所在。
> 注意延迟是以**接收端 poll 次数**注入的，拍数不等于毫秒；⑥ 里的实测 RTT 才是真实往返。

> 若源码放在 `/mnt/c/...` 下，建议先拷到 WSL 的 ext4（如 `~/mc`）再构建，
> 避免跨文件系统的 I/O 开销与权限问题。

### 测单线程负载（性能基线）

上位机的界面刷新、取窗抽稀、收帧解码全在**同一个线程**上跑。这条基线就是量它有多少余量：

```bash
cmake -S . -B build-rel -DCMAKE_BUILD_TYPE=Release
cmake --build build-rel -j"$(nproc)"
QT_QPA_PLATFORM=offscreen ./build-rel/host/mc_host_bench --seconds=5
```

它把设备侧的产帧周期设成 10 ms（与 tick 同频）与 1 ms（10 倍压力）两档各跑一遍，
打印每拍处理耗时与拍间隔的 P50/P95/P99、界面刷新成本、整页绘制成本、实测帧率与环形缓冲覆盖数。
**它刻意不进 `ctest`** —— 它回答的是"在这台机器上量到多少"，不是"对不对"。
实测数字、测量条件、复现命令与未覆盖面见 `docs/PERF.md`。

### 持续集成

`.github/workflows/ci.yml` 在每次推送与 PR 上跑四个 job（环境固定 `ubuntu-22.04`，与本地验证环境对齐）：

| job | 干什么 |
|---|---|
| 源码指纹与测试报告一致性 | 重算源码聚合指纹，与 `docs/TEST_REPORT.md` §1 记录的值比对 —— 源码改了而报告没跟着更新就判失败（即"这份报告描述的确实是这份源码"） |
| 协议核心（无 Qt） | 在**没装 Qt6** 的机器上构建并跑测试，顺带断言 `host/` 按 ADR-001 被安静跳过、且三个核心二进制的 Qt 依赖命中为 0 |
| 固件核心（宿主测试 + PTY 端到端） | 独立构建 `firmware/`，跑 20 条宿主测试（含一条真 PTY 端到端） |

## 设计要点

**`libmc_core` 刻意零 Qt 依赖。** 上位机与虚拟设备模拟器链接**同一份**协议实现，
因此两端协议不一致的 bug 从"可能发生"变成"不可能发生"；
同时核心逻辑可以用纯 GoogleTest 测试，不需要安装 Qt 就能验证（ADR-001：核心库零 Qt 依赖，
构建时找不到 Qt 会安静跳过 `host/`，协议核心照样能构建与测试）。

**协议不用 ASCII 文本。** 一行 ASCII 文本指令没有帧头、校验、序号、应答与超时。
新协议是带 CRC-16/CCITT-FALSE 的二进制帧，详见 `docs/PROTOCOL.md`。

**运动指令不自动重传。** `START` / `SET_TARGET` 超时后进入 `Fault` 等待人工确认，
绝不自动重发——重发一条可能已被丢弃的运动指令会产生未定义运动。
只有幂等命令（`SET_PID` / `SET_MODE` / `HELLO`）允许重传。详见协议文档 §5。

**"允许重传"必须真的重发出去。** 重传的**判定**归 `AckTracker`，但把帧重新推上线路的动作
得有人做 —— 增量 6 修掉了这个缺口：`pump()` 在判出 `TxOutcome::Retry` 的那一拍
按**同一 `seq`、同一载荷**重发（设备侧去重窗口据此把"已执行过的那次"变成重放应答）。
只判不发的后果很隐蔽：请求会一直挂在等待表里，而调用方因为 `canRegister` 已为 false，
连自己重发都做不到。

**设备状态由状态机裁决，不是现算的投影。** 7 个状态与命令门禁统一放在零 Qt 的
`mc/device_state.hpp`，UI / 模拟器 / 固件共用同一份。其中一条容易漏掉的规则：
**故障一旦置位就只能由"人工确认"清除** —— 否则
`Fault → 链路断 → 重连 → 握手成功 → Ready` 会把故障顺手洗掉，
而这**恰好是最容易发生的那条路径**（设备出事 → 人过去拔线 → 重新上电 → 界面一切正常）。
详见协议文档 §5.3。

**设备侧通信丢失保护（F7）。** 运行中静默超过窗口就撤销目标、限幅停车并进入 `Fault`。
窗口必须**长于**上位机心跳周期，否则健康链路上设备会自己跳故障；取 3000 ms
（与"连丢 3 拍判链路失效"同口径）。⚠️ 这是**模拟器里已验证的语义**；
固件已烧录并跑通真串口会话，但**拔线触发 F7 这条路径尚未在实物上验证**。详见协议文档 §5.4。

**会话生命周期收在上位机里，但不自己发明失效检测。** `HostSession` 里有一个三态
（未就绪 / 握手中 / 就绪）的小层，只做三件事：未就绪时发首个 `HELLO`、收到**配对上的**
`HELLO_ACK` 才转就绪、链路失效或一轮 `HELLO` 重试用尽就退避重开一轮。
链路**是否失效**仍然只由 `LinkMonitor` 判定，它只消费结论 —— 所以没开链路监控时，
本层看不出失效，这不是遗漏而是"不重复造检测"的代价。
三条红线都写成了断言而不是注释：重连成功**绝不**自动恢复运动（设备停在 `Fault`/`Ready`，
要人工再来一次）；断链路径上**绝不**重发已登记的运动指令；在途请求一律以**超时**结清，
绝不静默丢弃。详见协议文档 §5.5。

**环形缓冲与解码暂存区是两种不同的工具。** 遥测显示用有界环形缓冲（允许丢旧数据），
协议解码用不会丢字节的暂存区（丢字节 = 解析错）。不可互换。

**上位机分五层，但通信层刻意"没有新代码"。** 层 1 界面 → 层 2 应用服务（`DeviceManager`）
→ 层 3 通信（`mc::HostSession` + `mc::ITransport`，**直接复用核心库**）→ 层 4 设备抽象
（`IDevice` / `SimulatedDevice`）→ 层 5 数据（`TelemetryRing` / `CurveModel`）。
只有层 2 与层 4 是新代码：层 2 用 `QTimer`（10 ms，`Qt::PreciseTimer`）驱动 `IDevice::tick()`，
是**唯一**调用 tick 的地方；层 4 把 `DeviceSimulator` 接在回环链路的另一端。
于是"接真串口"与"接进程内模拟器"共用同一套界面与命令路径 —— 换成 `QSerialPort` 时只换层 4 的实现。

**界面上的每个控件都必须能显示结果。** 任务书写着"禁止仅实现界面而没有业务逻辑"，
落到这里的判据是：每个按钮点下去，命令行表格里必须出现一条**带归宿**的记录
（已确认 / 被拒绝 + 原因 / 超时 / 单向无应答）。所以控制控件**只按"会话是否就绪"禁用，
不按设备状态禁用** —— 运行中改模式本来就会被设备拒（`IllegalState`），把按钮灰掉反而让人
永远看不到"为什么被拒"。让拒绝发生、把原因显示出来，信息量更大。
唯一的例外是 `STOP`：它只要求链路开着，会话没就绪也允许发 —— 把手动停车挡在一个"未就绪"
的会话后面，恰恰是最危险的时刻。

**界面刷新是单线程定频的，这是有意的，而且余量已经实测。** 遥测进环形缓冲，界面按 20 Hz
（`kUiRefreshDivider = 5`）取窗、抽稀、重绘。让 100 Hz 的数据直接驱动 100 Hz 的重绘，
是把 CPU 花在看不见的差别上。这条"单线程 + 定频刷新"的**基线已经量出来**
（`docs/PERF.md`）：设备侧产 1 kHz 遥测、环形缓冲写满的最坏一档下，跨 7 次运行每拍处理耗时
P50 14–19 µs、P99 ≤ 473 µs、单拍最大 944 µs —— 按最坏观测值也只有 10 ms 拍预算的 9.4%，
拍间隔稳在 10.0–11.0 ms，单核占用约 6%。**四条"该考虑拆线程"的门槛一条都没触到，
所以当前不开线程** —— 先有基线再谈优化，且不拿线程安全的复杂度去换一个量不出来的收益。
曲线页把"缓冲条数 / 本拍画出点数 / tick 次数 / 重绘次数"并排显示，节流有没有生效一眼可查。

**曲线抽稀用 min/max 分桶，不是等间隔取样。** 等间隔取样会让一闪而过的尖峰从图上消失，
而尖峰（过速、限位、故障前的抖动）恰恰是监控最该看见的东西。每桶保留极小与极大，
并**按时间顺序**输出（桶内乱序会让折线自己打结）。三条曲线**各用自己的纵轴刻度**：
速度是 deg/s、位置是 deg，共用一根轴的话 0–300 deg/s 在 0–10000 deg 旁边就是一条贴底的直线。

**绘图控件是自绘的，不是引入库。** 三个原因：① **不引入第三方绘图库依赖** ——
产物零外部图库（`ldd` 可核对）；② 需要的能力很小 —— 三条折线 + 网格 + 图例，
一百多行 `QPainter` 就够；③ 任务书本来就要展示"环形缓冲 + 抽稀 + 定频刷新"，自绘反而把这件事
摆在明面上。绘制与数据也**刻意分开**：`CurvePlot` 只画，取窗与抽稀在 `curve_model` 里、
可无头测试。

**双轴协调是"速度缩放式同步"，不是插补。** 多轴在真机上就是**多台驱动器**、各挂各的链路，
协议里每条命令也只认一个轴 —— 所以"轴组"是**上位机侧**的一层编排，协议不用改、设备侧
甚至不需要知道"组"这件事。做法是：按最长行程定公共时长 T，每轴速度 = 行程 / T，
于是同时出发即同时到达，且没有一轴超过上限。⚠️ 它**中间不约束两轴的轨迹关系**
（那才是插补，要设备侧按插补周期分发同步位置），而且单线程下"同时"的含义只是
**两轴命令落在同一拍（10 ms）**，偏差不超过一拍 —— 这一点必须如实说，不能写成"严格同步"。
编排里还有一道**全组安全闸**：任一轴进故障或链路失效就立刻 `STOP` 全组 ——
一台轴停了另一台还在走，对机械就是被拧一下。它**排在其他所有判断之前**。

**运行日志与报警、审计是三条独立的流。** 三者都在记"发生了什么"，但不是一回事：
报警是**需要人处理**的事（有级别、要确认、会拦启动）；审计是**人做了 / 试了什么**
（追责用的流水，被拒的也要记）；日志是**程序自己走过哪些路**（最多、最细、可以随时丢）。
把三者合成一条流的后果很具体：每拍一条的排查信息会把"必须处理的那一条"淹掉 ——
而人恰恰是在出事的时候才去看。所以日志页上调级别**不会让报警消失、也不会少一条审计流水**，
反过来也一样。实现上刻意**不引入第三方日志库**：需要的只有"分级 + 过滤 + 环形 + 轮转"，
两百行以内；过滤发生在**入口**（被级别挡掉的不进环形、也不格式化），
环形满了丢最旧的并**把丢弃数显示出来**（只说"最后 512 条"而不说丢了多少，会让人以为那就是全部）。

## ⚠️ 安全声明

**本系统的软件停止功能不能替代物理急停或硬件安全保护。**

上位机的 `STOP` 按钮、以及设备侧的任何软件保护，都只在软件层面生效：
它们依赖通信链路、微控制器与电源正常。**必须另行提供独立的物理急停回路与硬件保护**
（如 H 桥使能脚的硬件切断），不得把软件停止当作唯一的安全手段。

## 限制与诚实声明

- **硬件已接入，验证到速度闭环**：实机为 STM32F103C8T6（Blue Pill）+ ST-Link V2 +
  CH340 USB-TTL + TB6612FNG + N20 6 V 1:100 编码器电机（2800 计数/输出轴转）。
  已验证：OpenOCD 烧录 `Verify OK`、真串口会话（遥测 0 拒收）、开环驱动、
  编码器速度闭环（目标 200 deg/s，实测 202 deg/s，误差 1%）。
- **真机尚未验证的部分**：位置环定位；反向/双向（固件已支持 `AIN2=PB0`，
  **接线需从 GND 改到 PB0，改接与反向实测待做**）；真机回零与软限位
  （编码器无 Z 相，回零仍是软件逻辑）；真机拔线后的通信丢失保护；长时间运行稳定性。
  这些场景在宿主测试与模拟器里已覆盖语义，但**不能当作硬件实测**。
  ⚠️ 在带负载或无人值守运行前必须先在实物上验证 F7（通信丢失保护）：宿主测试覆盖了
  "静默超窗 → 故障锁存"，但真实电机与驱动器上的行为**未验证**。
- **双轴协调没有两台真实驱动器**：它是在**两台进程内模拟器**上验证的。
  "同时到达"的数学是穷举验证过的；但"两轴同时出发"只在单线程一拍（10 ms）之内成立
  （偏差不超过一拍），**不是严格同步、也不是插补**。真机上多轴需要多条串口：
  代码路径支持（每轴可独立换成串口数据源），但没有硬件可验。
- **运行日志只在本地文件系统上验过**：磁盘写满、目录权限变化、多进程写同一个日志文件
  这些情况**未测**；日志类**不做线程安全**（设计上由单线程持有）。
