# 通信协议（当前 v3）

> 状态：**这份文档是线格式的权威**（`kProtocolVersion = 0x03`）
> 冻结日期：2026-10-16（v1）／2026-10-17（v2、v3，见 §8 的版本演进表）
> 实现：`common/`（`libmc_core`），已由 GoogleTest 全量覆盖（数量随用例增加而变，不在此处钉数字）
> 适用：上位机（Qt6）↔ 真实 STM32 固件 ↔ 虚拟设备模拟器

---

## 1. 设计目标

早期实现常用纯 ASCII 行文本：没有帧头、没有校验、没有序号、没有应答、没有超时。
本协议要解决这些问题，并满足：

| 目标 | 手段 |
|---|---|
| 能判断一帧是否被破坏 | CRC-16/CCITT-FALSE 覆盖除帧头外的全部字节 |
| 能发现丢帧/乱序/重复 | 16 位序列号 |
| 能在字节流里重新找到帧边界 | 固定 2 字节 SOF + 长度字段 + 逐字节重同步 |
| 长度不可信时也不崩 | LEN 上限 1024，**超限在分配内存之前就拒绝** |
| 运动指令不被盲目重发 | 按消息语义区分"需应答"与"可重传"（§5） |
| 两端协议实现不可能不一致 | 上位机与模拟器**链接同一份** `libmc_core`（ADR-001） |

## 2. 物理层

| 项 | 值 |
|---|---|
| 接口 | USART3（PB10 = TX / PB11 = RX） |
| 参数 | 115200 bps / 8 数据位 / 1 停止位 / 无校验 / 无流控 |
| 字节序 | 全部多字节字段为**小端** |
| 帧间隔 | 无要求（靠 SOF + 长度分帧，不依赖空闲线检测） |

**带宽核算**：100 Hz 遥测 × (10 字节头 + 21 字节载荷 + 2 字节 CRC) = **3.3 kB/s**，
占 115200 bps（≈11.5 kB/s）的 **约 29%**，余量充足。

## 3. 帧结构

| 偏移 | 长度 | 字段 | 类型 | 说明 |
|---:|---:|---|---|---|
| 0 | 2 | `SOF` | `uint8[2]` | 固定 `0xAA 0x55` |
| 2 | 1 | `VER` | `uint8` | 协议版本，当前 `0x03`（演进见 §8） |
| 3 | 1 | `TYPE` | `uint8` | 消息类型；**bit7 = 1 表示应答帧** |
| 4 | 2 | `SEQ` | `uint16` LE | 序列号，`0…65535` 循环回绕 |
| 6 | 2 | `LEN` | `uint16` LE | 载荷长度，上限 **1024** |
| 8 | `LEN` | `PAYLOAD` | `uint8[LEN]` | 载荷 |
| 8+`LEN` | 2 | `CRC16` | `uint16` LE | CRC-16/CCITT-FALSE |

**CRC 覆盖范围**：从 `VER`（偏移 2）到 `PAYLOAD` 末字节，**不含 SOF**。
即覆盖 `6 + LEN` 个字节。

| 帧尺寸 | 值 |
|---|---|
| 头部 | 8 字节 |
| 尾部 | 2 字节 |
| **最小帧**（空载荷） | **10 字节** |
| 最大帧（1024 载荷） | 1034 字节 |

### 3.1 CRC 参数

| 参数 | 值 |
|---|---|
| 算法 | CRC-16/CCITT-FALSE |
| 多项式 | `0x1021` |
| 初值 | `0xFFFF` |
| 输入反转 | 否 |
| 输出反转 | 否 |
| 结果异或 | `0x0000` |
| **标准校验向量** | `crc16("123456789") == 0x29B1` |

> 这条标准向量是**唯一的外部权威锚点**。
> 实测结论（见 `docs/TEST_REPORT.md` 变异测试）：把多项式改成 `0x8005` 后，
> 39 个用例中**只有** `Crc16.StandardCheckVector` 变红 ——
> 因为编解码两端用同一个错误多项式时，往返自洽，其余用例全都察觉不到。
> **没有这条向量，错误的 CRC 参数会完全隐形，只有在与真实设备对接时才炸。**

### 3.2 载荷线格式

**逐字段显式序列化，不对结构体做 `memcpy`。**
理由：编译器会在结构体里插 padding，且不同 ABI / 编译选项下 padding 可能不同 ——
`memcpy` 一个结构体上线，等于把本机的 ABI 细节写进协议。
`mc::Nack`（`uint16` + `uint8`）就是这个问题的实例：**内存占 4 字节，线长只有 3 字节**，
`payload.hpp` 里用 `static_assert` 把这条关系钉住了。

浮点按 **IEEE-754 单精度**的位模式走线，小端。
（`static_assert(std::numeric_limits<float>::is_iec559)` 保证不做静默假定。）

| 载荷 | 线长 | 字段布局（小端） |
|---|---:|---|
| `Telemetry` | 21 | `timestampMs` u32 @0 · `velocityDegPerSec` f32 @4 · `positionDeg` f32 @8 · `target` f32 @12 · `state` u8 @16 · `faultCode` u8 @17 · `pwmOutput` u16 @18 · `statusFlags` u8 @20 |
| `SetPid` | 12 | `kp` f32 @0 · `ki` f32 @4 · `kd` f32 @8 |
| `SetTarget` | 4 | `target` f32 @0 |
| `SetMode` | 1 | `mode` u8 @0（0 = 停止控制，1 = 速度环，2 = 位置环） |
| `ClearFault` | 1 | `faultCode` u8 @0（操作员**确认的那个**故障码；0 不是合法确认） |
| `HomeParam` | 8 | `speedDegPerSec` f32 @0（> 0，幅值） · `timeoutMs` u32 @4 |
| `SoftLimits` | 9 | `enabled` u8 @0 · `minDeg` f32 @1 · `maxDeg` f32 @5 |
| `ParamState` | 26 | `mode` u8 @0 · `target` f32 @1 · `kp` f32 @5 · `ki` f32 @9 · `kd` f32 @13 · `limits`（上面那 9 字节）@17 |
| `Nack` | 3 | `rejectedSeq` u16 @0 · `reason` u8 @2 |

`Telemetry.statusFlags`（v3 起）目前只定义一位：

| 位 | 名称 | 含义 |
|---|---|---|
| `0x01` | 本轮回零已建立零点 | **进入回零时清零、零点建立时置位** |

它必须由设备**持续**报，不能靠上位机从状态推：HOME 的应答只说明"回零开始了"，
而"走到位"与"半路被 STOP 打断"在状态上都可能落到 `Ready`（见 §5.3）。
语义与 CiA402 的 *Homing attained* 一致：它说的是"**这一轮**成没成"，
不是"这台机器历史上回过零"。

**未定义的位一律忽略**（与 `state` / `faultCode` 一样不参与语义校验）：
将来设备多发一位，不该让旧上位机把 100 Hz 的帧判成坏数据 —— 那等于把整条曲线的
数据源掐断。

`Nack.reason` 取值：`0` 未指明 · `1` 未知类型 · `2` 当前状态不允许 · `3` 参数非法 · `4` CRC 错 · `5` 忙。

**结构性校验与语义校验是两件事，刻意分开**：

| 层级 | 函数 | 判什么 | 失败含义 |
|---|---|---|---|
| 结构 | `decodeXxx()` | 长度对不对 | **线格式错**（帧本身不该被产出） |
| 语义 | `isXxxValid()` | 有限性、取值范围 | **业务层要拒的**（设备发来了荒谬值） |

典型例子：`NaN` 的 4 个字节是**完全合法**的 float32，长度没问题，所以
`decodeTelemetry()` 会成功返回；但它是传感器坏掉或除零的信号，
`isTelemetryValid()` 必须判否 —— **绝不能把 NaN 当成正常速度画到曲线上**。
这条边界由 `Payload.NonFiniteTelemetryDecodesButFailsValidation` 用例守着。

## 4. 消息类型

| TYPE | 名称 | 方向 | 载荷 | 需应答 | 可重传 |
|---|---|---|---|---|---|
| `0x01` | `HELLO` | 双向 | 设备信息 | 是 | 是 |
| `0x02` | `HEARTBEAT` | 双向 | 空 | 是 | 否 |
| `0x10` | `SET_MODE` | 上→下 | 模式号 | 是 | 是 |
| `0x11` | `START` | 上→下 | 空 | 是 | **否** |
| `0x12` | `STOP` | 上→下 | 空 | **否** | **否** |
| `0x13` | `SET_TARGET` | 上→下 | 目标值 | 是 | **否** |
| `0x14` | `SET_PID` | 上→下 | kp/ki/kd | 是 | 是 |
| `0x15` | `CLEAR_FAULT` | 上→下 | 确认的故障码（1 字节） | 是 | 是 |
| `0x16` | `READ_PARAMS` | 上→下 | **空**（非空即拒） | 是 | 是 |
| `0x17` | `HOME` | 上→下 | 回零速度 + 时限（8 字节） | 是 | **否** |
| `0x18` | `SET_LIMITS` | 上→下 | 软限位一组（9 字节） | 是 | 是 |
| `0x20` | `TELEMETRY` | 下→上 | 21 字节遥测 | **否** | 否 |
| `0x21` | `FAULT_EVENT` | 下→上 | 故障码 | 否（周期重发） | 否 |
| `0x7F` | `NAK` | 双向 | 被拒的 SEQ + 错误码 | — | — |
| `0x81` | `HELLO_ACK` | 应答 | | | |
| `0x82` | `HEARTBEAT_ACK` | 应答 | | | |
| `0x90` | `SET_MODE_ACK` | 应答 | | | |
| `0x91` | `START_ACK` | 应答 | | | |
| `0x93` | `SET_TARGET_ACK` | 应答 | | | |
| `0x94` | `SET_PID_ACK` | 应答 | | | |
| `0x95` | `CLEAR_FAULT_ACK` | 应答 | | | |
| `0x96` | `READ_PARAMS_ACK` | 应答 | 设备实存参数（26 字节） | | |
| `0x97` | `HOME_ACK` | 应答 | | | |
| `0x98` | `SET_LIMITS_ACK` | 应答 | | | |

三条需要单独说清楚的报文：

**`READ_PARAMS`（0x16）** 回答的是"设备**存着**的是什么"，而不是"我发出去的是什么"。
它是配方下装的最后一步（下装完逐字段核对），也是界面上"我设的到底落地了没有"
唯一的凭据。它的载荷必须为空：非空说明对端与我们对格式的理解不一致，
回 `NAK(BadParameter)` 比猜它想读什么安全 —— 一个猜错的"读回结果"比一次拒绝危险得多。

**`HOME`（0x17）** 让设备以**给定的低速**朝零点走，到位之后把那里**定义成**零点。
它必须在设备侧完成，不能用 `SET_MODE` + `SET_TARGET` + `START` 拼：
"零点"是设备坐标系的知识（行程开关在哪、编码器 Z 相在哪），上位机拼出来的只是
"走去 0 度" —— 如果此刻坐标系本来就是错的，那等于朝一个错误的原点走。
速度取幅值，方向由设备判断；让上位机指定方向等于让一个看不见坐标系的人指挥电机往哪边撞。
`HOME_ACK` 只表示回零**开始了**，"零点建立没有"由 `TELEMETRY.statusFlags` 报（见 §3.2 与 §5.3）。

**`SET_LIMITS`（0x18）** 下发**位置**行程限制。设备存下来并据此拦，不是一条显示用的设置：
上位机可以因为"它以为是这个值"而少发一条命令，但真正拦住电机的必须是设备。
设备额外拒掉一类：**把当前位置关在门外**的限位（那是一句与事实矛盾的声明，
多半意味着符号/单位/轴号搞错，而后果是这台设备从此永远不能合法运行）。

`CLEAR_FAULT` 是**人工确认故障**这一步的报文：只有它能把 `Fault` 上的锁存位放行
（见 §5.3 的不变式 1）。载荷里带**被确认的那个故障码**，设备必须与它当前锁存的码比对，
不一致就回 `NAK(BadParameter)`：

> 不带码的"清一切"是危险的 —— 屏幕停在旧故障上时，这一下会把操作员**没看见的**新故障
> 悄悄清掉，而界面上还显示着"已确认清除"。确认只有针对一个具体的、被观察到的故障才有意义。

它**需要应答**（"清没清掉"不能靠猜），且属于**幂等**那一族（不含任何运动，
重复清除一个已清除的故障是无操作，`Fault` 之外的状态会被门禁拒掉）。

**请求与应答的配对**由 `tryAckOf()` 显式给出。没有配对的请求（`STOP`、`TELEMETRY`）
返回 `false`，**不使用"哨兵类型"表示缺失**。

**未知 TYPE 的处置归属应用层**：编解码层原样透传（`StreamDecoderTest.UnknownTypeIsPassedThroughToApplicationLayer` 固定了这一边界），
由应用层回 `NAK`。

### 4.1 帧头 SEQ 的相关规则

上位机需要一个**统一规则**来判断"这一帧是关于哪个请求的"：

| 响应类型 | 帧头 SEQ 的取值 |
|---|---|
| ACK（`0x81`…`0x95`） | **被应答请求的 seq**（ACK 无载荷，只能这样相关） |
| `NAK` | **被拒绝请求的 seq**（载荷里另有一份 `Nack.rejectedSeq`，是权威记录） |
| `TELEMETRY` | 设备自己的出站序号（与请求无关） |

NAK 的 seq 在帧头与载荷里各出现一次，属于有意冗余：帧头那份让上位机**不必解码载荷**就能做相关，
载荷那份保证载荷自包含。两者必须一致 —— 由 `EndToEnd.DeviceNackEchoesRejectedSeqInBothHeaderAndPayload` 断言。

**收到 NAK 必须停止等待该请求的 ACK**，否则会白等到超时，
甚至在超时后把一条已被明确拒绝的运动指令误判成"失控"。
该行为由 `AckTracker::cancelPending()` 实现，并由
`EndToEnd.SetModeWhileRunningIsRejectedWithIllegalState` 守着。

## 5. 应答与重传策略（安全关键）

这三条是本协议与"随便定个帧格式"的区别所在，取舍理由见 ADR-003 / ADR-004 / ADR-005。

| 规则 | 内容 | 理由 |
|---|---|---|
| **R1** | `STOP` 单向：无 ACK、不重传 | 停止是幂等的安全动作；等 ACK 只会延迟停机 |
| **R2** | `START` / `SET_TARGET` / `HOME` **需要 ACK，但绝不自动重传** | 重发一条可能已被丢弃的运动指令 = 未定义运动。超时 → 进入 `Fault`，**等待人工确认**（`HOME` 同理：重发一次回零会让已经动起来的那一趟再被下一次指令叠上去） |
| **R3** | `TELEMETRY` 不需要 ACK，允许丢帧 | 100 Hz 上报，丢一帧 10 ms 后就有新帧；为它重传会挤占控制指令带宽 |
| **R4** | `HEARTBEAT` 期待应答但**不重传** | 应答用于证明**双向**连通并测 RTT；但心跳本身周期性，丢一帧等下一周期即可 |
| **R5** | 只有幂等命令（`HELLO` / `SET_MODE` / `SET_PID` / `CLEAR_FAULT` / `READ_PARAMS` / `SET_LIMITS`）允许自动重传 | 重发不改变最终状态（`READ_PARAMS` 是纯读、`SET_LIMITS` 是"把行程设成这个值"，重复设同一个值等价于设一次） |
| **R6** | `FAULT_EVENT` **不需要应答**，故障期间周期性重发 | 它是通知不是请求。丢一帧下一拍就有新的；要求"已经出事的设备"还必须响应应答，是把可靠性押在最不可靠的一方身上 |

| **R7** | `HEARTBEAT` 超时**不算故障**（`TxOutcome::Dropped`），只是"漏了一拍" | 若按"超时即 Fault"处理，健康链路上丢一个心跳就会报警；链路是否失效应由"连续丢 N 拍"累计判定 |

上位机侧必须统计并显示 **丢帧数、CRC 错误数、重同步丢弃字节数**，
不得在界面上把"数据没到"显示成"速度为零"。

### 5.1 序列号去重的规则（设备侧）

设备记住最近 **32** 个处理过的 `(TYPE, SEQ)` 及其应答。命中即判为重传：
**重放上一次的应答**，但**不重复执行副作用**。

- **为什么必须重放应答**：只去重不重放的话，对端丢了 ACK 后重传会一个应答都拿不到，
  白等到超时 —— 幂等命令的重传机制会被去重机制废掉。
- **为什么 `HELLO` 要清空窗口**：上位机重启后会从 `SEQ=0` 重新编号，那些新命令会被
  当成上一次会话的重传而**静默吞掉**，表现为"握手成功但一条命令都不生效"。
- ⚠️ **`HELLO` 还必须绕过去重窗口本身**，否则上面那条清空会失效：上位机重启后仍从
  `SEQ=0` 发 `HELLO`，而窗口里恰好还留着上一会话的 `(HELLO, 0)` —— 这条 `HELLO`
  会被当成重传直接回放掉，清空永远不会执行。这是个**自指的僵局**：
  用来对付重复的手段本身被重复挡住了。`HELLO` 没有业务副作用、且幂等，
  不做去重没有任何损失（应答丢了再来一次反而正是我们要的）。
- **窗口为什么是 32**：重传只可能发生在应答超时窗口之内（毫秒级），
  32 条命令的跨度远超该窗口；再大只是白占内存。

### 5.2 超时窗口按实测 RTT 配置

`AckTracker` 的超时窗口**不再硬编码**：由 `LinkMonitor` 用 `HEARTBEAT_ACK` 采样往返时间，
取样本窗口的 P95 × 300%，再夹到 `[50, 2000] ms`。一个样本都没有时**退回显式初值**
（`initialAckTimeoutMs`，默认 200 ms），绝不给激进的小值 —— 那会把健康的慢链路误判成超时。

心跳的应答**无条件**交给监控器（不依赖 `AckTracker` 是否还认领它）。否则会自举死锁：
初始窗口若小于真实 RTT，心跳先被判超时出队 → 监控器永远拿不到样本 → 窗口永不收敛。

> 这条是被实测逼出来的：把上行延迟加到超过旧的硬编码窗口（200 ms）之后，
> `START` / `SET_TARGET` 会被**误判**成超时 → `Fault`。
> 演示程序场景 ⑤（未开监控，判 Fault 2）与场景 ⑥（已开监控，判 Fault 0）是这件事的对照。

**心跳的 `seq` 必须与命令共用同一个计数器。** `AckTracker` 只按 `seq` 判重、不看类型，
两套计数器必然撞车，撞上之后命令会被 `canRegister` 前置检查拦住、**静默发不出去**。
因此 `HostSession::enableLinkMonitor()` 要求显式提供序列号来源。
握手层（§5.5）同理，且它必须与心跳、命令指向**同一个**计数器。

### 5.3 设备状态机与命令门禁（阶段 4）

状态机住在 `libmc_core`（`mc/device_state.hpp`），纯逻辑、不碰串口 / 时钟 / Qt。
**上位机 UI、模拟器、固件三处共用这一份裁决** —— 同一套规则写三份必然漂移。
正因为它是纯函数式的，`(8 状态 × 2 故障锁存位 × 12 事件) = 192` 个组合能被**逐格断言**。

| 值 | 状态 | 含义 |
|---|---|---|
| 0 | `Disconnected` | 链路断 / 端口未开 |
| 1 | `Initializing` | 已连上，等 `HELLO` 往返 |
| 2 | `Ready` | 握手完成，输出**未使能** |
| 3 | `Running` | 已使能 |
| 4 | `Stopping` | 收到 `STOP`，正把速度收敛到零 |
| 5 | `Fault` | 有故障：只允许 `STOP` / `HEARTBEAT` / `HELLO` / `READ_PARAMS` / `CLEAR_FAULT` |
| 6 | `Recovery` | 人工确认后的中间态，恢复校验通过才回 `Ready` |
| 7 | `Home` | 正在回零：电机在转，但**不接受任何目标值**，也不接受改模式 |

`Home` 与 `Running` 是两回事：都在让电机转，但回零追的是"零点"—— 一个由设备
定义的地方，而不是操作员给的目标。把它并进 `Running` 会让"现在这个运动是不是
操作员要的那个"说不清。

`TELEMETRY.state` 直接发这张表的编号，`kDeviceStateCount == 8`。
`TELEMETRY.fault_code`：`0=None` / `1=CommunicationLoss` / `2=OverSpeed` / `3=OverLimit` / `4=CrcBurst` / `5=Forced`（仅供测试注入） / `6=HomeFailed`。
故障码与报警代码表的对应关系由 `alarm.hpp` 里的 `static_assert` 钉住，两端不会各改一半。

**命令门禁**（只看状态，不看载荷；载荷合法性由 `isValidXxx` 负责）：

| 命令 | 放行于 | 理由 |
|---|---|---|
| `HELLO` / `HEARTBEAT` / `STOP` / `READ_PARAMS` | **全部状态** | 会话起点 / 探活 / 幂等安全动作 / **什么都不改变**。堵掉任一个都是自毁：堵 `HELLO` 就没有断线重连，堵 `STOP` 就没有安全通道；`READ_PARAMS` 不改任何东西，塞进门禁表只会多一格说不清理由的格子 |
| `SET_PID` / `SET_LIMITS` | `Ready` `Running` `Stopping` | 改的是**参数**，不改变目标值本身：在线整定是本项目的核心用法，而收紧/放宽行程也不该逼着人先停机 |
| `SET_TARGET` | `Ready` `Running` | `Ready` 也放行的理由见下 |
| `START` / `HOME` | 仅 `Ready` | 两者都会让电机动起来；`HOME` 更严一格 —— 它的前提是"此刻没有别的运动目标" |
| `SET_MODE` | 仅 `Ready` | 见下 |
| `CLEAR_FAULT` | 仅 `Fault` | 见下 |
| 其余情况 | → `NAK`（`IllegalState`） | |

`Home` 状态下这四族（改模式、设目标、开动、改参数）**都不放行**：
回零是设备自己的一段流程，它的参数（速度 / 时限）在 `HOME` 报文里一次给全，
中途改什么都没有意义。唯一例外是 `STOP` —— 那正是"电机动着"的时刻，必须能停。

两条**非平凡**的门禁决定，都是安全取舍而不是图方便：

- **`SET_TARGET` 在 `Ready` 放行**：若只允许 `Running` 下设定目标，操作员就必须
  "先 `START` 再 `SET_TARGET`" —— 而 `START` 打开输出的那一刻用的是**上一次的旧目标**，
  电机会先朝那个值动一下。"先设目标、再启动"没有这个瞬动。
- **`SET_MODE` 只在 `Ready` 放行**：`SET_MODE` 会改变 `target` 的**单位语义**
  （速度环是 deg/s，位置环是 deg）。运动中切模式，等于把同一个数值换成了另一种含义。
- **`CLEAR_FAULT` 只在 `Fault` 放行**：放行的条件是"**此刻正停在故障态**"，
  而不是"锁存位还挂着"。两者不等价 —— 拔线后重连前，锁存位仍在但状态是
  `Disconnected`/`Initializing`，此时该做的是把链路接回来（重握手会直接回到 `Fault`），
  而不是在一条发不出命令的链路上点确认。`Recovery` 里也不放行：那说明人工确认
  已经做过了，正等自检结果，再确认一次没有意义。
  其余状态一律 `NAK(IllegalState)` —— **绝不能用一句"已清除"把"没有故障可清"说成
  "清成功了一次"**。

**不变式**：

1. `Fault` **只能**经「人工确认 → `Recovery` → 恢复校验通过」离开，**绝不自动复位**。
   线路上唯一能表达"人工确认"的就是 `CLEAR_FAULT`；`RecoveryOk`（恢复校验通过）
   由设备自己产生，没有对应的报文。
2. 由 1 推出：故障必须**锁存**。若不锁存，
   `Fault ──链路断──► Disconnected ──重连──► Initializing ──握手──► Ready`
   会把故障顺手洗掉 —— 而这**恰好是最容易发生的那条路径**：设备出事 → 人跑过去拔线 →
   重新上电 → 界面显示一切正常。锁存位只能由 `RecoveryOk` 清除。
3. `STOP` 在任何状态都被接受；`Running` 与 `Home` 会因此转到 `Stopping`
   （`Ready`/`Fault`/`Recovery` 收到 `STOP` 不改变状态——那里本来就没有电机在动）。
   **从 `Home` 被打断这一趟，不算建立过零点**：回零是被"停下"这件事终止的，
   而不是走到了位。装置要靠 §3.2 的那一位状态位如实报出来，不能因为
   "最后停在了 `Ready`"就当成回零成功（见 §3.2 与 `HomeStatus` 的收尾判定）。
4. `Stopping → Ready` 的依据是「速度已收敛到门限内」，因为 `STOP` 单向无应答，
   设备拿不到"已停"的回执，只能自己把这件事翻译成一次状态迁移。

### 5.4 设备侧通信丢失保护（F7）

设备判定"上位机还活着"的**唯一依据**是「最近有没有收到过**一帧能过 CRC 的帧**」——
不是"收到过字节"：线上一直有噪声但一帧都过不了 CRC，那不叫通信正常。

`Running` 下静默超过 `kDeviceCommLossTimeoutMs` 时：撤销目标 → 按 `accelDegPerSec2`
限幅收敛到零（可控停车，不是把 PWM 一刀切断）→ 进入 `Fault`（锁存，需人工确认）。

⚠️ **这个窗口必须长于上位机的心跳周期**，否则心跳之间的空档就会被判成丢线 ——
链路完全正常，设备自己跳 `Fault`。取 **3000 ms** = 上位机允许连丢 3 拍，
与 `LinkMonitor::missedBeatsToDeclareLinkDown` 同口径。
代价是设备最多带着陈旧目标再跑 3 s；更快的检测（UART 错误/空闲中断）属固件侧改造。
这个定值由 `DeviceState.CommLossWindowMustOutlastTheHostHeartbeatPeriod` 钉住。

### 5.5 会话生命周期（上位机侧握手与重连）

`HostSession` 里有一个三态小层（`NotReady` / `Handshaking` / `Ready`），只负责三件事：
未就绪时发首个 `HELLO`、收到**配对上的** `HELLO_ACK` 才转就绪、一轮失败或链路失效后退避重开。
它是**可选**能力：不调用 `enableHandshake()` 时 `pump()` 的行为与本增量之前完全一致。

| 事件 | 处置 |
|---|---|
| 未就绪，且退避已到点 | 发一个 `HELLO`（`seq` 取自与命令共用的计数器），转「握手中」 |
| 收到**配对上的** `HELLO_ACK` | 转「就绪」，退避复位为初值 |
| 一轮 `HELLO` 重试用尽（`AckTracker` 判 `Fault`） | 转「未就绪」，退避 `×2`（上限 1600 ms）后重开一轮 |
| `LinkMonitor` 判链路失效 | **作废会话**（转「未就绪」）并立刻重开一轮 |

**不自己发明失效检测。** 链路是否失效只由 `LinkMonitor`（连续丢 N 拍）判定，本层只消费结论。
代价是**没开链路监控时本层看不出失效** —— 一个已就绪的会话不会被自动作废。
这不是遗漏，而是"不重复造检测"的必然结果。
（一个"只要收到 ACK 就算就绪"的假握手更糟：线上随便一帧陈旧应答就能把下发闸门打开，
所以就绪**只**由配对上的 `HELLO_ACK` 触发。）

**不设总轮数上限。**「要不要放弃」是上位机（人）的决定；本层只如实报 `handshakeRounds()`，
不替调用方想通之后静默停手。退避只保证"不会拿固定周期对着断链猛打"。

三条安全红线（都写成断言，不是注释）：

1. **重连成功绝不自动恢复运动。** 回连后设备停在 `Fault` 或 `Ready`，要人工再来一次 `START`。
   特别注意 `HELLO` **不会**洗掉故障锁存（§5.3 不变式 2），
   所以"重连 → 设备又转起来"在这套协议里不可能发生。
2. **断链路径上绝不重发已登记的运动指令。** 这不是靠某处判断把着，而是靠机制：
   `START` / `SET_TARGET` 不是 `isRetryable`，`AckTracker` 根本不会为它们产出
   `TxOutcome::Retry`，重发用的"发件留底"里也永远没有它们。
3. **在途请求一律以超时结清。** 会话作废时**不做**任何清空 —— 静默丢弃会让一条运动指令
   既不报超时也不报应答、凭空消失；而 ADR-003 要求它超时就是一个**安全事件**，必须被上报。

**"判了可重传"必须真的重发。** 判定归 `AckTracker`，把帧重新推上线路的动作归 `pump()`：
它在判出 `TxOutcome::Retry` 的那一拍按**同一 `seq`、同一载荷**重发，
对端去重窗口（§5.1）据此**重放应答**而不是重复执行。
只判不发会让请求永远挂在等待表里，而调用方因为 `canRegister` 已为 false，
连自己重发都做不到（`sendXxx` 会直接返回 false）。

## 6. 异常场景处置（对照任务书第三阶段要求）

| 场景 | 处置 | 依据 |
|---|---|---|
| 串口断开 | 状态机 → `Disconnected`；停止发送，标记数据不可信 | 阶段 4 |
| 不完整帧 | 保留在暂存区，等后续字节；暂存区上限 1034 字节 | `pending()` 有界 |
| CRC 错误 | 丢弃该帧，`framesCrcError++`，**从当前字节的下一个字节重新找 SOF** | 逐字节重同步 |
| 前导垃圾字节 | 逐字节跳过并计数（`bytesDiscarded`），直到找到 SOF | `GarbagePrefixIsCountedAndResynced` |
| `LEN` 超限 | **在读 LEN 之后、分配内存之前**拒绝并重同步 | `OversizeLengthIsRejectedWithoutBuffering` |
| 版本不兼容 | CRC 通过 ⇒ 是完整帧，整帧跳过并计 `framesBadVersion`（不逐字节重同步） | `VersionMismatchSkipsWholeFrameWithoutResync` |
| 重复命令 | 设备按 `(TYPE, SEQ)` 窗口判重：**重放应答、不重复执行**；`HELLO` 清空窗口 | §5.1 |
| 心跳漏拍 | `TxOutcome::Dropped`，**不计为故障**；连续丢 N 拍才判链路失效 | §5 R7 |
| 链路时延导致误判超时 | 心跳实测 RTT → 窗口按 3×RTT 撑开（此前是硬编码 200 ms） | §5.2 |
| 命令超时 | `START`/`SET_TARGET` → `Fault` + 人工确认；幂等命令 → 重传 | §5 R2/R5 |
| 设备重新上电 | 心跳/遥测中断 → 判链路失效 → 会话作废 → 退避重开一轮 → 发 `HELLO` 重握手（设备侧回到 `Initializing`，带锁存故障则落回 `Fault`） | §5.5 |
| 重连成功之后 | 设备停在 `Fault`/`Ready`，**绝不**自动恢复运动；要人工再来一次 `START` | §5.5 红线 1 |
| 上下位机状态不一致 | 以设备回读为准（`HELLO_ACK` + 参数回读），拒绝"假定一致" | 阶段 4 |

## 7. 与 Q1/Q2/Q3 待裁定项的关系

本协议**不依赖**绘图库与许可证的选择。若最终决定改用其它传输（如 TCP），
只需替换 `Transport` 层（`IDevice` 抽象，阶段 2），帧格式与 `libmc_core` 不动。

## 8. 版本演进规则

1. 新增 `TYPE` 值：**不**提升 `VER`（旧端收到未知类型回 `NAK`，行为可预期）。
2. 修改帧头布局、CRC 参数、或改变既有类型的语义：**必须**提升 `VER`。
3. 本文件是协议的唯一真源。代码中的常量必须与本表逐一对应；
   对应关系由 `FrameCodec.EncodedLayoutMatchesSpec` 用例钉住。

### 8.1 已经发生过的三次演进

| `VER` | 日期 | 相对上一版改了什么 | 为什么这算"改线格式" |
|---|---|---|---|
| `0x01` | 2026-10-16 | 初版：帧头 + CRC + 序号 + 遥测 20 字节 | —— |
| `0x02` | 2026-10-17 | 新增 `READ_PARAMS`/`READ_PARAMS_ACK`（载荷 `ParamState` 26 字节）与 `SET_LIMITS`/`SET_LIMITS_ACK`（载荷 `SoftLimits` 9 字节）；`ParamState` 起带软限位 | 新增的是**类型**，照规则 1 本可不升 `VER`；但 `ParamState` 把软限位包进了既有语义的扩展里，且 `SET_LIMITS` 让 `Ready` 之外的运行中可以收紧行程，属于"改变既有行为"——按规则 2 提升 |
| `0x03` | 2026-10-17 | `TELEMETRY` 载荷 20 → **21** 字节，尾部加 1 字节 `statusFlags`（当前只定义位 0「本轮回零已建立零点」） | 这是**既有类型的定长载荷变长**：旧上位机按 20 字节解，会与 CRC/长度对不上，必须靠 `VER` 分流，不能靠"多发一字节也许对方忽略" |

**`VER` 不匹配时怎么处置**：CRC 通过说明这是一条**完整**帧（不是噪声），
所以整帧跳过并计 `framesBadVersion`，**不做逐字节重同步**——
在一条完整帧里逐字节找 `SOF`，反而可能从前导的 `0xAA 0x55` 里切出一个假帧头。
上例由 `VersionMismatchSkipsWholeFrameWithoutResync` 用例守着（见 §6）。

> 反面教材：改线格式却不动 `VER`，等于让"版本号"这个字段从此刻起不再表示任何东西。
> 两端一旦真的按不同长度解同一类帧，表现是"帧全丢、CRC 全错"，
> 而现场看到的现象却是"连上了但什么都没显示"——最难查的一类故障。
