# 性能基线 —— 上位机单线程负载实测

> 测量日期：2026-10-16
> 被测对象：`mc_host`（Qt6 上位机，Release 构建）+ 进程内模拟设备（`SimulatorConfig` 只改产帧周期）
> 测量工具：`mc_host_bench`（`host/src/bench_main.cpp`，随源码一起构建，不是另做一份）
> 一句话结论：**单线程余量充裕** —— 跨 7 次运行，最坏观测值是每拍处理耗时
> **P99 473 µs、单拍最大 944 µs**，即按最坏值也只有 10 ms 拍预算的 **4.7% / 9.4%**；
> 典型值（P50）在 8–19 µs；拍间隔稳在 10.0–11.0 ms。
> **当前不需要开线程**（第 3 步暂缓的实测依据）。

---

## 1. 为什么先要有这一份

任务书要求"任何性能优化都必须有优化前后的实测数据"。**没有基线，优化前后两栏都是空的**；
更要紧的是"要不要拆线程"这个决定如果只凭感觉，结论只能是"拆了显得更专业"。

所以第 1 步做的不是优化，是**造一个可复现的压力源 + 量出当前基线**：
按本文的数字决定后面该不该动、动哪里；如果数据显示没有瓶颈，就如实写"没有瓶颈"。

## 2. 测量条件（以及这条基线**不**代表什么）

| 项 | 值 |
|---|---|
| CPU | `Intel(R) Core(TM) i5-14600KF`（`nproc` = 20） |
| 系统 | Windows 10 + WSL2 `Ubuntu-22.04`（源码在 `/mnt/c`，构建目录 `build-wsl-rel`） |
| 编译器 / 构建 | `g++ 11.4.0`，`-DCMAKE_BUILD_TYPE=Release`（`-O3 -DNDEBUG`） |
| Qt | `6.2.4` |
| 图形平台 | `QT_QPA_PLATFORM=offscreen`（**不是真显示**） |
| 链路段 | **进程内回环**（`LoopbackTransport`），**不是真实串口** |
| 设备 | 进程内模拟器；除 `telemetryPeriodMs` 外全用默认参数 |

**必须附带的四条限定**（引用本文任何数字时都要一起带上）：

1. **不是硬件指标，也不是发布版本指标。** 链路是进程内回环、设备是模拟器、
   平台是离屏渲染。真正的串口吞吐与真实显示下的绘制开销**都没有测**。
2. **1 kHz 这一档在当前的串口上根本跑不起来。** 一帧遥测 30 B，1 kHz 即 30 kB/s ≈
   **300 kbaud**（8N1，10 bit/B）；而项目协议里的 USART3 是 **115200 baud**，只够
   ≈ **384 帧/s**。所以 1 kHz 压的是**上位机的收帧/解码/CRC/缓冲这条 CPU 路径**，
   不是"链路能跑 1 kHz"——那是算得出来说不通的。
3. **补发的帧内容相同。** 设备侧运动模型一拍只积分一次，补发出来的那 10 帧之间没有新的
   采样点。它们是**帧率压力**，不代表真实设备那种"每个采样点都不同"的遥测密度。
4. **这些数字对机器负载敏感，必须报区间而不是单值。** 实测同一个二进制、同一项指标，
   不同次运行能差出一倍以上（见 §4 开头）。**在同一个脚本里"构建 + 跑测试 + 起 bench"，
   测出来的就是"机器忙的时候有多慢"，不是这台机器的能力。**

## 3. 怎么复现

```bash
cmake -S . -B build-rel -DCMAKE_BUILD_TYPE=Release
cmake --build build-rel -j"$(nproc)"

# 先确认机器不忙，再单独跑（不要和构建/测试并发）
cat /proc/loadavg
QT_QPA_PLATFORM=offscreen ./build-rel/host/mc_host_bench --seconds=5     # 两档各 5 s
QT_QPA_PLATFORM=offscreen ./build-rel/host/mc_host_bench --seconds=45    # 长跑：把环形缓冲填满
```

**跑多次**（本文的数字是 5 s 档 4 次 + 45 s 档 3 次），报区间与最坏值。
`--seconds=45` 那档是为了让环形缓冲（容量 4096 ≈ 41 s @100 Hz）真的写满，
从而把"取窗 + 抽稀"推到窗口内样本数的上界 —— 5 s 档测不到这个成本。

- 不设 `QT_QPA_PLATFORM` 时程序**自己**设 `offscreen`（任何机器上都能跑）；
  想在真显示下测，自己 `QT_QPA_PLATFORM=xcb` 再跑一次即可。
- 用 Debug 构建跑也没关系，但程序会自己打一条警告：那些数字**不是**发布口径。
- `mc_host_bench` **刻意不进 `ctest`**：它输出的是"这台机器上量到多少"，不是"对不对"。
  正确性判据（补发有没有真的生效）在单测里，那边是确定的。

### 压力是怎么造出来的

设备侧原本是"每拍最多发一帧遥测"，那样把产帧周期设到 1 ms 也只能得到 100 Hz ——
实际帧率变成了**上位机的取数节奏**，等于用上位机的 tick 率伪装成了链路能力。
本轮把产帧改成**按设备自己的周期补发**（每次来取，把这段时间该发的都发出来），
单拍上限 16 帧（16 × 30 B = 480 B < 单次交换上限 512 B），超出部分丢弃并计数。
于是"设备产帧周期"第一次成了一个**独立于上位机 tick 的自变量**，
100 Hz 与 1 kHz 才是两档真正不同的负载。

## 4. 实测结果

**先说清楚口径：这些数字报的是「多次运行的区间」，不是单次结果。**
性能测量对机器负载敏感 —— 本机（Windows 侧同时有别的活动）同一个二进制的同一项指标，
不同次运行能差出一倍以上。所以下面每一格给**多次运行的最小–最大**，
最坏值才是拿来判断"够不够用"的那个数。

共跑了 **7 次**：5 s 档 4 次、45 s 档 3 次。其中 45 s 档有一次明显被外部负载污染
（整页绘制 P50 从 1.3 ms 涨到 3.1 ms、每拍耗时 P99 从 221 µs 涨到 473 µs），
**该次仍计入区间** —— 把它剔掉只会让结论更好看，而"机器忙的时候会怎样"正是要看的。

## 5. 从数字里能读出什么

**① 1 kHz 遥测只让每拍中位数多花约 6–8 µs。** 8–10 → 15–18 µs。
折算下来**每多收一帧（30 B，含 CRC 与解码）约 0.7 µs**。也就是说：把遥测率提高 10 倍，
在这台机器上换来的代价是每拍百分之几。

**② 最坏一拍离预算还很远。** 拍预算是 10 ms；跨 7 次运行，P99 最大 473 µs（**4.7%**）、
单拍最大 944 µs（**9.4%**）。P99 明显高于 P50，原因不是遥测，而是：每 5 拍里有 1 拍的
`statsRefreshed` 会**同步**执行界面的取窗/抽稀/更新控件（45 s 档约 25 µs，见 ⑤），
再叠上定时器自身的抖动与外部负载。

**③ 拍间隔说明定时器基本没被抢占。** P50 恒为 10000 µs、P95/P99 恒为 11000 µs ——
`Qt::PreciseTimer` 的抖动被压在 1 ms 以内，**且不随遥测率变化**。
7 次运行里只在 45 s 档出现过两次单点延迟（15000 / 17000 µs），
出现在被外部负载污染的那两次运行里 —— 那是宿主机调度的影响，不是本程序算得更久了。

**④ 两档的环形缓冲增长速度完全不同 —— 这是设计，不是巧合。**
45 s 档下 1 kHz 与 100 Hz 写进缓冲的条数几乎一样（4096 满 + 丢弃 373–378），
因为 `DeviceTick` 一拍只交出一条样本（"本拍最后一帧"），界面侧的取样率恒等于 tick 率。
所以"遥测 1 kHz"增加的是**收帧/解码/校验的负载**，不是绘制负载。
这一点在引用这些数字时必须说清 —— 否则容易读成"1 kHz 也不影响画图"，
而实际是"1 kHz 的数据根本没进画图那条路"。

> **顺带解释一个看起来像丢帧的差额。** 某次 45 s 运行里上位机收了 **4469 帧**，
> 而缓冲只写进 **3856 条**（另外两次是 4096 + 丢弃 ≈ 4471 条，正好等于拍数）。
> 差额有两个原因叠在一起：① 上位机把 `QElapsedTimer::elapsed()` 的**整毫秒数**当 tick
> 时刻传下去，真实间隔贴着 10 ms 时读数会 ±1 ms 抖动 —— 一条 9 ms 的步长让某拍收不到帧，
> 后面的 11 ms 步长又补回来，于是每拍产帧数在 **0/1/2** 之间抖、**平均恒为 1.000**；
> ② 缓冲按设计**一拍只收最后一帧**，所以它记的是"有帧的那几拍"的条数。
> **协议侧一帧都没丢**（收帧数、解码数、拒收数、CRC 错都没变）。
> 这条性质已经写成用例钉住：
> `EndToEnd.MillisecondQuantizedClockDithersTheFrameCountWithoutLosingAny`。

**⑤ 界面刷新成本随窗口内的样本数走，不随遥测率走。**
5 s 档（窗口内约 500 个样本）是 **3–5 µs**；45 s 档（缓冲写满、30 s 窗口内约 3000 个样本）
是 **24–31 µs**。抽稀预算 900 点/通道，所以这是"从 3000 个点里挑 900 个"的成本。
窗口内样本数有天花板（环形缓冲 4096 条），所以这项成本**有上界**，不会无限增长。

**⑥ 绘制成本与数据量无关，约 1.3–1.5 ms/次（安静时）。**
安静环境下四个场景的 `grab()` P50 都在 1290–1471 µs，差异在噪声范围内 ——
说明这一层的开销**几乎全是布局与控件自身的绘制**，不是三条曲线的那点折线。
被外部负载污染的那次涨到 3093 µs，正好说明它跟数据无关、跟机器忙不忙有关。
按 20 Hz 刷新、每次重绘 1 次算，绘制约占单核 **2.6–3.0%**。
（`grab()` 在离屏平台下画进后备存储，真显示下的合成开销未测。）

**⑦ 把三块加起来：** 45 s 档最坏条件下单核占用约
`100 拍/s × 66 µs（含刷新的均值上限）+ 40 次绘制/s × 1.35 ms ≈ 0.7% + 5.4% ≈ 6%`；
把绘制换成污染值（3.1 ms）则约 13%。
**单线程还有十几倍余量。**

**⑧ 界面的节流确实在生效**：刷新信号稳定在 19.8–20.0 次/s（分频 5），
而遥测是 100–1000 帧/s。

## 6. 什么时候才轮到"拆线程"（第 3 步的进入条件）

用本文的数字把门槛写死，免得后面凭感觉改架构（下表"当前实测"取**跨 7 次运行的最坏值**）：

| 触发条件 | 当前实测（最坏） | 结论 |
|---|---|---|
| 每拍耗时 P99 ≥ 10 ms 的 20%（2 ms） | 473 µs（**4.7%**） | 不触 |
| 每拍耗时最大值 ≥ 拍周期（10 ms，即丢拍） | 944 µs（9.4%） | 不触 |
| 拍间隔 P99 明显超过 10 ms 的 1.5 倍（15 ms） | 11000 µs（仅两次单点延迟 15/17 ms，均在外部负载污染的运行里） | 不触 |
| 界面刷新 + 绘制合计 ≥ 单核 30% | 约 6%（污染时约 13%） | 不触 |

**四条全不触 → 当前不开线程。** 真要把架构推到"多线程"，得先有一个**真实**的、
把这几条推到门槛上的场景（例如真串口 460800 baud 下的实际帧率、或真显示下的绘制开销）。
在那之前，拆线程只会用线程安全的复杂度换一个量不出来的收益。

## 7. 未覆盖面（不得据此宣称的部分）

| 项 | 状态 |
|---|---|
| 真实串口吞吐 / 时延 | ❌ **未测**。链路是进程内回环；115200 baud 下的实际帧率只有**算出来的上限**（≈384 帧/s），没有实测 |

| 内存占用 / 常驻集 | ❌ 未测 |
| 长时间稳定性 | ❌ 未做（最长一次 45 s） |
| 其他平台 / 编译器 | ❌ 仅 `g++ 11 / Linux x86-64`；MSVC / clang / ARM 未测 |
| 设备侧（STM32 固件）性能 | ❌ **完全未测**。本文全部数字来自上位机与进程内模拟器，与固件无关 |
